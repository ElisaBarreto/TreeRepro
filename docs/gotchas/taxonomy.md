# GBIF taxonomy lookup

## `checklistKey` on the v2 match service rejects WCVP
**Symptom:** `GET https://api.gbif.org/v2/species/match?scientificName=Quercus%20robur&checklistKey=f382f0ce-323a-4091-bb9f-add557f3a9a2` answers `HTTP 400 "Unrecognized checklistKey. No matching service available for this checklistKey."`, although the same key resolves fine at `GET /v1/dataset/<key>` (title "The World Checklist of Vascular Plants (WCVP)", type CHECKLIST).
**Cause:** The v2 match service accepts only a short allowlist of checklists, and WCVP is not on it under any of its known keys (its GBIF dataset key, its ChecklistBank key `2232`, or the Fabaceae variant). `datasetKey=` is silently ignored by both v1 and v2 the same way — nothing tells the caller the parameter did nothing.
**Fix:** WCVP is a v1 dataset-scoped name search, not a v2 checklist match: `GET https://api.gbif.org/v1/species?datasetKey=<WCVP_GBIF_DATASET_KEY>&name=<encoded>&limit=5`. It is a different endpoint with a different answer shape (`results: [{ key, scientificName, taxonomicStatus, ... }]`, no `diagnostics` block), mapped separately from the v2 backbone match (RFC-81 R1, R2). The name sent must be canonical only: `name=Quercus robur L.` (with authorship) returns `results: []`.

## `VARIANT`, not `FUZZY`, is what a misspelling actually returns
**Symptom:** A `z.enum(['EXACT', 'FUZZY', 'HIGHERRANK', 'NONE'])` on `matchType` throws on every misspelt proposal in production, despite passing every test written against the plan's assumed shape.
**Cause:** Probed live against nine names (2026-09-19), the v2 backbone returns `EXACT`, `VARIANT`, `HIGHERRANK` and `NONE` — never `FUZZY`. `Quercus robour` (misspelling of `Quercus robur`) comes back `matchType: 'VARIANT'`, `confidence: 93`, `rank: 'SPECIES'`. `FUZZY` is documented by GBIF but was never observed; `VARIANT` is what a misspelling actually produces.
**Fix:** `matchType` is `z.enum(['EXACT', 'VARIANT', 'FUZZY', 'HIGHERRANK', 'NONE'])` (both are treated the same for the `fuzzy` verdict), and the verdict computation keys off **rank**, never off `matchType` alone: `exact` requires `matchType === 'EXACT'` **and** `rank === 'SPECIES'`. `Quercus` (the genus name itself) returns `matchType: 'EXACT'` at `rank: 'GENUS'` — an `EXACT` match that is not a species match, and must not read as "exact match" on a proposal card. A `matchType` outside the known set (a value GBIF adds later) maps to `'NONE'` rather than throwing, because a stored `lookup` jsonb is re-read long after the call that produced it (`gbifToMatch`/`wcvpToMatch` in `apps/api/src/integrations/taxonomy.ts`).

## WCVP's `results[0]` is not the right taxon
**Symptom:** Approving a species proposal for `Pinus sylvestris` attaches the wrong taxon (key `207484214`, a `MISAPPLIED` usage of `Pinus sylvestris Thunb.` whose `acceptedKey` points at `Pinus thunbergii`) instead of the real `Pinus sylvestris L.` (key `207484307`, `taxonomicStatus: 'ACCEPTED'`).
**Cause:** `GET /v1/species?datasetKey=<WCVP>&name=Pinus%20sylvestris` returns the `MISAPPLIED` row before the `ACCEPTED` one — `results` is not sorted by taxonomic status, and taking `results[0]` blindly picks up whichever WCVP happened to index first.
**Fix:** Select the first result whose `taxonomicStatus === 'ACCEPTED'`; fall back to `results[0]` only when none of the results is `ACCEPTED` (`wcvpToMatch`). Pinned by a regression test reading the captured fixture `apps/api/src/integrations/fixtures/gbif/wcvp-misapplied-first.json`, so a future refactor that reaches back for `results[0]` fails loudly instead of silently attaching the wrong species.
