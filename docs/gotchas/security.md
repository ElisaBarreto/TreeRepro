# Security

Lessons of the 2026-09-19 audit (issue #120). Each one is a pattern the next weak spot will come from, not a bug that is still open; the guard rails named under **Fix** are what keeps it closed.

## A permission to manage permissions is root unless the RFC caps it
**Symptom:** `users.update` or `roles.manage` handed to a manager so they can onboard people, and the manager can now grant themselves `admin` — or add any permission to a role they hold and receive it on the next request (issue #118 F-02).
**Cause:** RBAC checks that the actor holds the permission the route names and nothing more. A permission that changes roles or their permission sets is therefore worth the whole catalog unless a rule says which grants it may not make. The code was correct against the RFC; the RFC had no ceiling.
**Fix:** RFC-31 R12–R14: only `admin` grants or removes `admin`, an actor never changes their own roles nor the permission set of a role they hold, and a refused change is audited (`recordingRefusal`, `apps/api/src/access/roles.ts`). When a new permission lets its holder shape access — roles, plots assignment, delegation of any kind — write the ceiling into the RFC before the route, and test the escalation path (actor grants themselves, actor widens a role they hold) as a failing test first.

## A route that returns rows takes a `Visibility`, even when it is a file
**Symptom:** A plot-bound contributor downloads `GET /api/export/accepted.csv` and the file holds every species, including the ones the JSON routes hide from them (issue #118 F-01). The same shape waits in any new download, report, e-mail digest or admin aggregate.
**Cause:** RFC-33's two-viewer test was written for "every service that reads species, traits, levels or records", and the export predates the contract, calling its query with `UNRESTRICTED`. Nothing tied the obligation to the *route*, so a route that reaches the tables through its own query, or through a cache, slipped past the rule and past the review.
**Fix:** RFC-33 R3 lists every route that returns dataset rows in any form and RFC-33 R9 demands the two-viewer test per route. RFC-33 R10 makes the list executable: `apps/api/src/routes-visibility.integration.test.ts` calls every route guarded by a dataset-reading permission (`VISIBILITY_GUARDED_PERMISSIONS`, `apps/api/src/http/visibility-routes.ts`) and fails unless the handler resolved `visibilityOf` — or the route sits on `VISIBILITY_EXEMPT_ROUTES` with the rule that exempts it. A new route behind `dataset.read`, `dataset.export`, `coverage.read`, `records.review` or `contributions.read` fails that test until it takes a `Visibility` or is added to the list with an RFC citation; a route behind a new permission is added to the constant, never left out of it. `UNRESTRICTED` belongs in production code only where a rule names the exception: the visibility-blind counters of RFC-33 R3 (`admin/health.ts`, `jobs/digest.ts`), a writer re-reading the row it just wrote (`dataset/catalog.ts`, `dataset/curation.ts`) and `setAccepted` (RFC-33 R5, RFC-65 R6). Cite the rule in a comment when adding another; a read on behalf of a viewer never takes it.

## An e-mail is `users.read` data wherever it appears
**Symptom:** `GET /api/plots/:id/users` (behind `plots.manage`) listed each member's e-mail address, so a plot manager without `users.read` read addresses the user list would refuse them (issue #119 F-04). A new endpoint that "names a person" tends to reach for the address by habit.
**Cause:** The permission catalog binds `users.read` to `/api/admin/users`, not to the data. A response item built from a join on `users` carries whatever columns the query selects, and nothing stopped `email` from being one of them on a route guarded by something else.
**Fix:** RFC-02 R14: outside the viewer's own `GET /api/auth/me` and the flows that take an address as input, only routes guarded by `users.read` return one; any other item that names a person carries `id`, `name` and the fields its own RFC lists. When a new response names a person, select the columns by name and leave `email` out unless the route is `users.read`; the SPA links the name to the user page only for a viewer who holds `users.read`. The same principle holds for every other PII column (RFC-40): a permission on one route does not travel with the data to another.

## The SPA's permission gates and the API's checks drift apart silently
**Symptom:** A button appears for a viewer the API will answer 403 (a gate on a key no route enforces), or a gate names a retired key (`users.delete`) that no role grants any more and hides the action from everyone.
**Cause:** `hasPermission(me, '<key>')` in `apps/web/src` is typed against `PermissionKey`, which catches a typo but neither a retired key nor one the API never checks; the 2026-09-19 audit matched the 37 gates to their routes by hand, which no later change repeats.
**Fix:** RFC-32 R8, enforced by `pnpm rfc:check` (`tools/rfc-lint/src/gates.ts`): every key the SPA tests — `hasPermission(…)`, a nav entry's `permission:`, `permissions.includes(…)` — must be in the RFC-30 catalog and be enforced under `apps/api/src`, as a `requirePermission(ctx, '<key>')` guard or a `permissions.has('<key>')` / `currentPermissions(c).has('<key>')` check inside a handler (the lint reads tokens: another receiver, a comment or a string does not count); `admin.access` is the only exception (RFC-30 R4) and the lint fails if the SPA stops testing it. A new SPA gate on a key the API does not check is a lint failure, not a review note.
