# RFC-52 — Platform health

| Field | Value |
|---|---|
| Status | draft |
| Category | admin |
| Supersedes | — |

## Context

An administrator today reads the platform's condition off several separate screens — users, dataset totals, the curation queues, the two background jobs, imports. This RFC gives `health.read` holders one route that answers all of it in a single snapshot — counts, ids and timestamps, plus the operational text of the newest job runs and imports, never personal data (R2) — cached briefly because it is read often and changes slowly.

## Rules

- **R1** `GET /api/admin/health` (`health.read`) answers `{ users: { active, invited, suspended, signedInLast7d, signedInLast30d }, dataset: { species, activeSpecies, traits, activeTraits, references, records, coverageCells, validatedCells }, activity: { records7d, annotations7d, proposals7d, byDay: [{ day, records, annotations }] (14 days) }, queues: { pendingGroups, contested, proposals }, jobs: { auditPurge: <run>, digest: <run> } (the newest `job_runs` row per kind as `{ startedAt, finishedAt, status, detail, error } | null`), imports: [<RFC-64 R11 item> … 5 newest], computedAt }`. `imports` items are `healthImportSchema` — the RFC-64 R11 item without `runBy` (a name is PII, R2). `signedInLast7d` and `signedInLast30d` count distinct `actor_user_id` over the audit log's `auth.login.success` entries in the window; that sign-in count is **one indexed query** — a claim about that statement alone, not about the payload as a whole — because the existing `audit_log_at_idx (at desc)` serves its `at >=` predicate and bounds the scan to the window before the unindexed `action` filter applies; no new index is added for it, and none of the other statements of this payload is claimed to be index-served (see Open questions for the activity window, which is not). `dataset.records` is `sum(species_trait_coverage.record_count)` and `dataset.references` is a flat `count(*)` over `bibliographic_references` (it has no `active` column) — the same definitions `computeDatasetStats` already gives these numbers; no number in this codebase carries a second definition. `dataset.coverageCells` is the count of species × trait cells that have at least one record and `dataset.validatedCells` is the count that are validated (RFC-63 R11), so that `validatedCells <= coverageCells <= activeSpecies * activeTraits` always holds. Both are measured over the **active** catalog — active species × active traits, the same grid for every caller — which is what makes that invariant hold and what the health page's completeness meter divides by; they therefore differ from the totals the coverage page shows an administrator, who holds `dataset.read_inactive` and so sees the full grid including deactivated species and traits. A documented difference between two pages, not a disagreement between two numbers. The eight `dataset` numbers therefore mix two populations on purpose, and every surface that shows them side by side must say which is which: `species`, `traits`, `references` and `records` count the **whole catalog**, deactivated rows included, while `activeSpecies`, `activeTraits`, `coverageCells` and `validatedCells` count the **active** catalog only. The health page marks each of those tiles `(all)` or `(active)` in its label, so that the adjacency is legible rather than misleading — the same concern that settles `activity.records7d` below. `activity.records7d` and `byDay.records` count records of **every origin**, not manual entry alone, matching `dataset.records`, which also counts every origin — two adjacent numbers counting different populations would read as a bug. `activity.proposals7d` counts proposals **created** in the 7-day window; `queues.proposals` counts **open** proposals — two different numbers from two different queries, never interchanged. The payload is global: computed once with no per-viewer visibility or permission gate applied to any number, which is also what makes one shared cache entry correct for every caller. Cached one minute in Redis under the key `health` (a fixed key, not per-viewer, per R above); a cache read that misses computes and stores a fresh value with a 60 second TTL.
- **R2** No personal data: no `name`, `email`, `ip` or `userAgent` key anywhere in the payload, which the test in `health.test.ts` pins by walking every key path (objects, arrays, nullables, the `detail` record) and asserting none of those four keys occurs at any leaf. That is the rule this route actually enforces — not "counts, ids and timestamps only", the payload's original summary, which R1's shape (above) shows is no longer literally true: `imports[].fileName`, `imports[].error`, `imports[].unknownLevels[].value` and the job runs' `detail` field all carry free text alongside the counts, ids and timestamps. The one field of the import item that was personal data was `runBy` — a person's name — and R1 already removes it for exactly that reason; what remains is operational and dataset content, not personal data: a filename from an upload, an exception message from an import run, an unrecognized trait-level value read off a spreadsheet. Keeping it is deliberate, not an oversight this rule failed to catch: `health.read` is admin-only, and the same administrator can already open `/app/imports/$id` and see the whole batch, `runBy` included, so dropping `fileName` from health would close no access for anyone; and a health page whose imports table and job rows carried only ids and timestamps would be unreadable by a human — the failed filename and the failure text are exactly the signal an operations page exists to surface.
  Because this text is not shape-checked, the guarantee rests on the writer, not the schema — `job_runs.detail` is typed `z.record(z.string(), z.unknown())`, so the key-path walk structurally cannot constrain what is inside it, and the same is true of every other free-text field this route publishes verbatim. `digest.ts`, `audit/retention.ts`, the import job, and any future writer of a `job_runs` row or an import batch must keep `detail`, `fileName`, `unknownLevels[].value` and the import batch's `error` to operational content only — never a name, an email address, an IP or a user agent — one obligation stated once for every free-text field this payload surfaces, rather than re-derived per field as each is added. `job_runs.error` needs no such obligation: it is a failure code — identifiers only, never an exception message — by RFC-74 R1's `job_runs_error_check` (issue #114), so its guarantee is structural and this route publishes it as stored; the import batch's `error` is still exception text, and the writer obligation above is what keeps it clean. The route emits no audit entry.
- **R3** Job badge (web): both `jobs.auditPurge` and `jobs.digest` use one rule, so the two rows never diverge in meaning, and the rule is total over every `JobStatus` (`running`, `completed`, `failed`, `skipped`) plus the no-run case. Given a job's newest run: `never ran` when the run is `null`; red `failed` when `status` is `failed`, whichever job it is and whatever the run's age; otherwise (`completed`, `skipped`, or `running`) green, labelled with the status, when `startedAt` is within the last 26 hours, else amber `stale`. Neither daily job is a long-running batch, so a `running` row two minutes old is healthy and one still `running` after 26 hours is stuck — the same 26-hour grace window that separates a fresh completed run from a stale one separates those two cases too, and "stale" is the right word for a job stuck running past its expected cadence as much as for one that quietly stopped reporting.

Web (plan 12d): route `/app/admin/health` (nav **Health**, section Admin, permission `health.read`, icon `pulse`): tiles per group, a 14-day activity table, the two job rows badged per R3, the imports table linking to `/app/imports/$id`. Breadcrumb `Admin › Health`.

## Open questions

- If the sign-in window ever gets slow, the follow-up is a dedicated `(action, at desc)` index on `audit_log` — not needed today: `audit_log_at_idx` already bounds the 7/30-day scan before the `action` filter applies.
- The activity window is **not** index-served and is the first thing to watch. `trait_records` and `record_annotations` are each read twice by this route — once for the 7-day counts, once for the 14-day `byDay` series — and neither table carries an index on `created_at`; every index on both is on ids. If that window gets slow the follow-up is a `(created_at)` index on each, which is a schema change and so deliberately not carried by the plan that introduced this route. What bounds the cost today is the 60 second cache entry and the route being admin-only. The interaction to remember when judging that: the payload fires its statements concurrently against a pool whose default size is 10 (`apps/api/src/db/client.ts`), so a single cache miss can occupy every pooled connection for as long as those scans take, and the page's cost is paid by the rest of the API rather than by the administrator waiting for it. Since RFC-10 R15 that is one fill per miss, not one per concurrent request — misses that arrive while the fill runs await it instead of starting their own (issue #115) — but the fill itself still holds the pool for the duration of the scans. Measured on 2026-09-20 against the imported dataset (14 534 `trait_records`, 3.7 MB of heap, 473 pages; `record_annotations` empty): `EXPLAIN (ANALYZE, BUFFERS)` shows each of the two `trait_records` statements as a sequential scan of about 2.8 ms with every page already in shared buffers, so an index would save nothing a caller could notice and none was added (issue #116). Both tables are append-only and grow by manual entry, so the figure moves slowly; re-measure the same two statements when `trait_records` passes about a million rows or a cache miss of this route is seen to take longer than half a second, and add the two `(created_at)` indexes then.
