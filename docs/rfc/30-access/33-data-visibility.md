# RFC-33 — Data visibility

| Field | Value |
|---|---|
| Status | draft |
| Category | access control |
| Supersedes | — |

## Context

Some species and traits are not ready for the contributor community: traits still being defined, species outside the current phase or with unverified taxonomy. Contributors are recruited through field plots (RFC-67) and may be confined to them. The catalog therefore has row-level visibility, decided by the API for every read and write (RFC-02 R1), never by the web app.

## Rules

- **R1** Viewer. Every dataset read and write is evaluated for a *viewer*: the session user, their effective permissions (RFC-32 R1) and their plot settings (RFC-67). `Visibility` is the value `{ inactive: boolean, plotIds: string[] | null }`: `inactive` is true when the viewer holds `dataset.read_inactive`; `plotIds` is the viewer's assigned plots when `restrict_to_assigned_plots` is true, else `null` (no plot restriction). It is computed once per request by `visibilityOf(ctx, c)` and passed to every service call.
- **R2** A species is *visible* to a viewer when (`species.active` or `visibility.inactive`) and (`visibility.plotIds` is null or the species belongs to one of those plots). A trait is visible when `traits.active` or `visibility.inactive`. A level is visible when `trait_levels.active` or `visibility.inactive`. A record is visible when its species and its trait are visible, it is not withdrawn (RFC-63 R13), and its `harmonisation` is `harmonised` or the viewer holds `records.review` (pending records, unknown levels and the like are reviewer work). The unresolved-taxon flag (RFC-60 R6) is reviewer-only data too.
- **R3** Lists omit invisible rows: `GET /api/species`; `GET /api/genera` and `GET /api/families` (a genus or family with no visible species is omitted); `GET /api/traits` (invisible traits and levels omitted; an unrestricted viewer still receives everything with `active: false`); `GET /api/species/:id/traits`; `GET /api/records`; `GET /api/records/pending/traits`; `GET /api/records/pending`; `GET /api/records/disputed`. Counters are unaffected, whether stored or computed per request: a reference's `primaryCount`, `secondaryCount` and `recordCount` (RFC-61 R4) and a species' `traitCount` and `recordCount` (RFC-60 R7, RFC-69 R1) count every record that is not withdrawn (RFC-63 R13) for every viewer, so the visible parts beside them need not sum to them. The rule covers every route that returns dataset rows in any form — JSON, CSV, e-mail, cached aggregate — and this list is exhaustive: a new such route is added here (or to the exceptions below) before it is merged, so the review catches the omission. Beyond the routes above: `GET /api/species/:id` (RFC-60); `GET /api/traits/:id` and `GET /api/traits/:id/species` (RFC-62 R7, R8); `GET /api/references` and `GET /api/references/:id` (RFC-61); `GET /api/records/:id` (RFC-63); `GET /api/plots/:id/species` (RFC-67); `GET /api/coverage` and `GET /api/coverage/top` (RFC-69); `GET /api/me/contributions` and `GET /api/admin/users/:id/contributions` (RFC-71); `GET /api/me/dashboard` (RFC-72); `GET /api/export/dataset.zip` (RFC-66 R2) and, until plan 13i, `GET /api/export/records.csv` (RFC-66 R8). Exceptions, unrestricted by design and named as such in their RFCs: the global counters above and the trait dictionary's species counts (RFC-62 R5, R7); `GET /api/me/contributions/summary` and `GET /api/admin/users/:id/contributions/summary` (RFC-71 R4, R5); the daily digest e-mail (RFC-74 R3); the platform health payload (RFC-52).
- **R4** Detail routes answer 404 for an invisible row with the resource's code: `SPECIES_NOT_FOUND`, `TRAIT_NOT_FOUND`, `RECORD_NOT_FOUND`. The existence of an invisible row is never disclosed.
- **R5** Writes: `POST /api/records` and `POST /api/records/pending/map` on an invisible species, trait or level answer the same 404 / 400 as for an unknown one; `POST /api/records/:id/annotations` on an invisible record answers 404, and the level actions of RFC-65 R13 and R14 answer for an invisible species, trait or level what they answer for an unknown one. Catalog writes (`taxa.manage`, `traits.manage`, `references.manage`) take the same visibility; their holders are unrestricted by role design and the services do not assume it. `POST /api/records/pending/map` maps only the pending rows of visible species; the trait and its levels are checked the same way.
- **R6** Species scope (RFC-67): `GET /api/species` accepts `scope=plots|all` and `plotId=`. Default: `plots` when the viewer has at least one assigned plot and does not hold `dataset.read_inactive` (managers and admins have no plot-scoped home view), else `all`. `scope=plots` restricts the list to the species of the viewer's plots; `scope=all` lists every visible species; `plotId` restricts to one plot and ignores `scope`. A plot-bound viewer asking `scope=all`, or `plotId` of a plot they are not assigned to, answers 403 `PERMISSION_DENIED`. An unknown `plotId` answers 404 `PLOT_NOT_FOUND`.
- **R7** Representation: the species list item and detail carry `active: boolean` (RFC-60 R6, R7); the trait entry already carries `active`. A restricted viewer only ever receives `true`.
- **R8** `GET /api/auth/me` carries `scope: { plots: [{ id, code, name }], restricted: boolean }` (RFC-22 R10) so the web app can render the plot toggle and default the species list; presentation only (RFC-13 R3).
- **R9** Every service that reads species, traits, levels or records, and every route that returns dataset rows in any form (R3) — JSON, CSV, e-mail, cached aggregate — has an integration test with two viewers — one restricted, one unrestricted — over the same fixture (an inactive species with a record on an active trait; an active species with a record on an inactive trait) asserting omission versus presence. A route listed among the R3 exceptions has the test the other way round: both viewers receive the same rows.
- **R10** Meta-test. A test enumerates every registered route whose guard names one of the permissions that read the dataset — `dataset.read`, `dataset.export`, `coverage.read`, `records.review`, `contributions.read` (`VISIBILITY_GUARDED_PERMISSIONS`, `apps/api/src/http/visibility-routes.ts`) — calls each as an unrestricted viewer over a fixture that lets it succeed, and asserts that the handler resolved the viewer's visibility (R1: `visibilityOf` records the value on the request context), unless the route is on `VISIBILITY_EXEMPT_ROUTES` beside that constant. The exempt list names the routes behind those permissions that return no dataset rows, each citing its rule: `GET /api/me/contributions/summary` and `GET /api/admin/users/:id/contributions/summary` (RFC-71 R4, R5), `GET /api/plots` and `GET /api/plots/:id` (RFC-67 R3: plots are the recruitment structure, not scientific data). The test also fails on an exempt route that does not exist or that resolves visibility, so the list stays exact. R3 stays the human-readable list; this test is its executable form: a route behind one of those permissions that neither takes a `Visibility` nor sits on the exempt list fails the build.
