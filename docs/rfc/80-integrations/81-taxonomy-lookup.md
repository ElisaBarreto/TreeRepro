# RFC-81 — Taxonomy lookup

| Field | Value |
|---|---|
| Status | accepted |
| Category | integrations |
| Supersedes | — |

## Context

A species proposal (RFC-75) and the species dialog's **Look up** button both need to know what GBIF and the World Checklist of Vascular Plants (WCVP) call a proposed name, so a reviewer sees a match rather than a bare string. The obvious design — one GBIF **v2** match call per source, the second scoped to WCVP by `checklistKey` — does not work: verified live on 2026-09-19, `GET https://api.gbif.org/v2/species/match?scientificName=...&checklistKey=<WCVP key>` answers `HTTP 400 "Unrecognized checklistKey"`. The v2 match service accepts only a short allowlist of checklists and WCVP is not on it, under any of its known keys. This RFC documents the design that does work, verified against the live API on the same date: the GBIF backbone through v2 match, and WCVP through its own v1 dataset-scoped name search — two different endpoints, two different answer shapes, mapped into one shared result.

## Rules

- **R1** Client `ctx.taxonomy` (`TaxonomyClient.match(name)`) calls up to two sources, both on host `api.gbif.org`, so the fixed-host transport of RFC-80 R3/R6 (`redirect: 'manual'`, 5 s timeout, 1 MiB streamed cap, no retry) covers both with one allowed host; a fake client stands in for every test, which never reaches the network.
  1. GBIF backbone: `GET https://api.gbif.org/v2/species/match?scientificName=<encoded>`. Always attempted.
  2. WCVP: `GET https://api.gbif.org/v1/species?datasetKey=<WCVP_GBIF_DATASET_KEY>&name=<encoded>&limit=5`. Attempted only when `WCVP_GBIF_DATASET_KEY` is configured; default is empty, which skips the call and leaves the verdict (R3) to the backbone alone. The current key is `f382f0ce-323a-4091-bb9f-add557f3a9a2` (title "The World Checklist of Vascular Plants (WCVP)", type CHECKLIST; checked live 2026-09-19). The name sent is the canonical name only — a name carrying its authorship (e.g. `Quercus robur L.`) returns `results: []` from this endpoint, verified live.

  A start-up check (`GET https://api.gbif.org/v1/dataset/<key>`, `title` contains "World Checklist of Vascular Plants") runs once; on any failure it logs a warning and disables the WCVP call for the process (`null` in its place) — it never fails start-up, and there is no retry.
- **R2** Both sources map into the shared shape `TaxonMatch = { matchType, confidence, usageKey, acceptedUsageKey, scientificName, canonicalName, rank, status, family, genus, note }`; `usageKey` and `acceptedUsageKey` are strings (the backbone returns `usage.key` as a JSON string already; the WCVP mapper stringifies its numeric `key`/`acceptedKey`).
  - **Backbone** answer `{ usage: { key, name, canonicalName, rank, status }, acceptedUsage?, classification: [{ key, name, rank }], diagnostics: { matchType, confidence, note } }`: `matchType` is `diagnostics.matchType` narrowed to `'EXACT' | 'VARIANT' | 'FUZZY' | 'HIGHERRANK' | 'NONE'`; any other value GBIF might send maps to `'NONE'` rather than throwing, because the mapper is best-effort and a stored `lookup` is re-read long after this call (a value added later must not make an old proposal unreadable). `confidence` is `diagnostics.confidence`. `usageKey = usage.key`, `scientificName = usage.name`, `canonicalName = usage.canonicalName`, `rank = usage.rank`, `status = usage.status`; `family`/`genus` are the matching entries of `classification` by rank. `acceptedUsageKey = acceptedUsage?.key`. `note = diagnostics.note` when GBIF sends one (probed live, it never does); otherwise, when the matched rank is above species, a synthesised note naming the rank (e.g. `'matched the genus'`), and `null` at species rank — the same rule the WCVP mapping below applies, since GBIF supplies no note on either source.
  - **WCVP** answer `{ results: [{ key, scientificName, canonicalName, rank, taxonomicStatus, family, genus, acceptedKey?, accepted? }] }`: an empty `results` (HTTP 200, not an error) is a miss. Otherwise the selected row is the first with `taxonomicStatus === 'ACCEPTED'`, or the first row if none is `ACCEPTED` — `results[0]` is not reliably the right taxon: `name=Pinus sylvestris` returns the `MISAPPLIED` `Pinus sylvestris Thunb.` before the `ACCEPTED` `Pinus sylvestris L.`, and taking `results[0]` blindly would attach the wrong taxon to a proposal. From the selected row: `matchType` is `'EXACT'` when `rank === 'SPECIES'`, `'HIGHERRANK'` when the rank is above species, `'NONE'` when `results` was empty; `confidence` is always `null` (WCVP reports none); `usageKey = String(key)`, `scientificName`, `canonicalName`, `rank`, `family`, `genus` come straight off the row, `status = taxonomicStatus`; `acceptedUsageKey = acceptedKey == null ? null : String(acceptedKey)` (present on non-accepted rows). `note` is `null` at species rank, and otherwise names the matched rank (e.g. `'matched the genus'`) — WCVP has no `diagnostics` block, so this note is synthesised, not sourced.
  - **A 2xx whose body is not the shape above is a failed call, not an answer.** Each source's body is checked before it is mapped: the backbone must be an object carrying a `diagnostics.matchType` string, with `usage`/`acceptedUsage` objects and a `classification` array of objects if present at all (a `NONE` answer carries `diagnostics` alone, so those three are optional); the WCVP body must carry a `results` array whose rows are objects. A body failing its check makes that source `null` and counts as a failed call for R3, because the mappers are total by design — they degrade to nulls rather than throwing, so an unchecked malformed body would map to a `matchType 'NONE'` match, and R3 reserves `none` for a source that answered and found nothing. A structurally valid `results: []`, or a valid backbone body with no match, stays a genuine no-match. The check never throws and never fails the request.
  - The GBIF page link is `https://www.gbif.org/species/<usageKey>` for either source, with no `?checklistKey=` suffix: the WCVP source is a v1 dataset usage, not a v2 checklist match, so a checklist-scoped link does not apply to it.
- **R3** Stored `lookup`: `{ backbone: <R2> | null, wcvp: <R2> | null, verdict: 'exact' | 'fuzzy' | 'none' | 'failed' }`, computed over however many calls were attempted (one when `WCVP_GBIF_DATASET_KEY` is unset, otherwise two). `verdict` keys off rank, never off `matchType` alone: `exact` when either attempted-and-succeeded source has `matchType 'EXACT'` **and** `rank 'SPECIES'` (an `EXACT` match at genus rank — proposing `Quercus` itself — is not `exact`); `fuzzy`, when not `exact`, when either source's `matchType` is `'VARIANT'` or `'FUZZY'` (a misspelling comes back `VARIANT` from the live backbone, never `FUZZY`; both are treated the same); `none` when at least one attempted call succeeded and none produced an `exact` or `fuzzy` result (this covers a partial failure too — one call succeeding with no match while the other failed is still `none`); `failed` only when every attempted call failed outright — a non-2xx, a transport failure, or a 2xx whose body failed R2's shape check. A failing backbone call with WCVP disabled is therefore `failed`, not `none` — `none` is reserved for a call that succeeded and found nothing, which is an answer about the name, not a platform fault.
- **R4** The lookup is called only by proposal creation (RFC-75 R2) and by `GET /api/taxonomy/match?name=` (`taxa.manage`; rate limit 30 per minute per user, RFC-24 R3); the species dialog's **Look up** button in plan 12c fills the form from the answer. It never writes. A failure at this route answers 502 `TAXONOMY_LOOKUP_FAILED`; a proposal swallows the same failure into `lookup: null` instead (RFC-75 R2).

- 2026-09-19 — R2 and R3 amended: a 2xx whose body is not the documented shape is a failed call for that source, not a source that answered and found nothing. The mappers stay total (they degrade to nulls rather than throwing, since a stored `lookup` is re-read long after the call), so the check belongs one layer up, before the mapper: without it a malformed `classification` or a missing `results` produced a `matchType 'NONE'` match and a stored verdict of `none`, which is the `none`/`failed` conflation R3 exists to prevent — one is an answer about the name, the other is the platform's fault (code review).
- 2026-09-19 — R3 amended: `none`'s clause names the partial-failure case explicitly (one call succeeding with no match, the other failed) — the literal text covered only both-succeeded and both-failed, leaving that case undefined even though `verdictOf` and its tests already computed `none` for it correctly (code review).
