# RFC-10 — Architecture

| Field | Value |
|---|---|
| Status | accepted |
| Category | platform |
| Supersedes | — |

## Context

Design: `docs/specs/2026-09-12-foundation-design.md`. This RFC fixes the structural rules the code must follow.

## Rules

- **R1** The repository is a pnpm monorepo: `apps/api` (Hono HTTP API), `apps/web` (Vite + React SPA), `packages/contracts` (shared Zod schemas), `packages/config` (tsconfig bases), `tools/rfc-lint`, `infra/` (Docker, Caddy, Postgres init), `docs/`.
- **R2** Only `apps/api` connects to PostgreSQL and Redis and reads secrets. No other package imports a database or Redis driver.
- **R3** `apps/web` contains no business rules. It talks to the API only through `apps/web/src/api/client.ts`, which calls `/api/*` on the same origin with `credentials: 'include'`.
- **R4** Request and response shapes shared by API and web are Zod schemas in `packages/contracts`. The API validates with them; the web only derives types from them.
- **R5** Configuration is read only in `apps/api/src/config.ts`: non-secret values from environment variables (including the SMTP settings `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_FROM`, optional `SMTP_USER`), secrets from files (RFC-02 R6; `smtp_password` is read only when `SMTP_USER` is set). The result is validated with Zod; the process refuses to start on any invalid or missing value.
- **R6** Database access goes through Drizzle ORM. Raw SQL is allowed only through the `sql` template tag (parameterized); string concatenation into SQL is forbidden.
- **R7** Schema changes are SQL migration files in `apps/api/drizzle/`, generated by `drizzle-kit generate` (or `--custom` for hand-written SQL such as triggers) and applied by the `migrate` service before the API starts, using the `treerepro_migrator` role. The API runtime uses the `treerepro_app` role, which cannot create or alter tables. The `backup` service uses `treerepro_backup`, a read-only role (`pg_read_all_data`) that can write nothing. Role passwords are set only through client-side SCRAM verifiers (`\password`), never as plaintext in SQL text or process arguments.
- **R8** Runtime versions: Node 24 LTS, PostgreSQL 18, Redis 8, Caddy 2. Libraries are pinned exact in `package.json`.
- **R9** Production processes: `caddy` (only public port; TLS; serves the SPA; proxies `/api/*`), `api`, `postgres`, `redis`, `migrate` (one-shot, before `api`), `backup` (daily encrypted `pg_dump --no-owner --no-privileges` by `treerepro_backup`; optional `BACKUP_PING_URL` dead man's switch; restore procedure in `docs/gotchas/infra.md`). Development adds `web` (Vite dev server), `mailpit`, and publishes Postgres/Redis ports for inspection.
- **R10** Health endpoints: `GET /api/health` is public and answers exactly `{"ok":true}` (no envelope, no version, no dependency status). `GET /api/health/ready` checks PostgreSQL and Redis, answers `{"ok":true}` or 503 `SERVICE_UNAVAILABLE`, and is never proxied by Caddy (internal network only).
- **R11** Node executes TypeScript source directly in development (`node --watch --conditions=development`) and compiled JavaScript (`tsc` output in `dist/`) in production. `packages/contracts` exposes source under the `development` export condition and `dist/` by default.
- **R12** Every response carries an `X-Request-Id` header; the same ID is attached to every log line about that request. Middleware binds a child logger carrying the ID to the request context (`c.get('logger')`); request handling code logs only through it, so the ID is present by construction rather than by discipline.
- **R13** Operational commands live in `apps/api/src/cli/` and are run inside the API container: `seed:admin` (RFC-20 R8), `seed:traits` (RFC-62 R2), `import:records` (RFC-64 R1). In production they run as `node dist/cli/<name>.js`; files they read that are not TypeScript (`apps/api/seed/`) are copied into the image next to `dist/` and `drizzle/`.
- **R14** PostgreSQL extensions are created by migrations. `pg_trgm` (trusted; the migrator role has `CREATE` on the database) backs the substring searches of RFC-60 R6 and RFC-61 R4.
- **R15** Read-through cache. `cachedJson(redis, key, ttlSeconds, compute)` (`apps/api/src/redis/cache.ts`) stores `compute`'s result in Redis as `{ value, computedAt }` under `key` for `ttlSeconds`; a hit answers the stored entry without calling `compute`, and `forgetCached(redis, …keys)` deletes entries so the next call recomputes. Concurrent misses on one key share one fill: within one API process, the first miss runs `compute`, every call that arrives while that fill is in flight — whether before or after its own Redis read — awaits the same promise and answers the same entry (same `value`, same `computedAt`), and no second `compute` runs for that key. The in-flight check comes before the Redis read as well as after it: a call that reads Redis first could see a miss issued while the fill was running and answered after a failing fill released the key, and would then start a second `compute` for a request that arrived in time. When `compute` rejects, every waiter rejects with that error, nothing is stored, and the key is released so the next call computes again; a fill never blocks a different key. The coordination is in-process — a map of in-flight fills per Redis client, cleared when the fill settles — not a Redis lock: the API runs as one process (R9), so this bounds the fills a miss can cause to one; a deployment running N API processes would bound it to N, never to the number of concurrent requests, and would stay correct without a change — a cross-process lock would only make that bound tighter, at the price of a lock TTL, polling and a dead-holder case this design has no need to handle. Serving a stale entry while refreshing it is deliberately not offered: the misses that matter are cold (after a restart, after `forgetCached`), and there is nothing stale to serve. The stored entry is plaintext at rest (`docs/gotchas/infra.md`), so it carries no PII (RFC-40 R1).
- **R16** Every e-mail is sent multipart: a `text` part and an `html` part (`MailContent`, `apps/api/src/mail/templates.ts`). The text part is a complete reading on its own; the HTML part carries the same facts inside the one shared frame `emailLayout` builds (`apps/api/src/mail/layout.ts`): table-based, inline-styled, in the TreeRepro identity of `docs/specs/2026-09-12-visual-identity.md`. Every interpolated value — a name, a species, a trait value, a link — passes through `escapeHtml`, attribute values included, so nothing a user or a record supplies reaches the markup unescaped. Remote resources come only from `<APP_ORIGIN>/email/` (`apps/web/public/email`, served with the SPA): the emblem, the icons and the hero art as images — decorations a mail client would drop as SVG or positioned markup are baked into them — and Sora/Manrope as `@font-face` (clients that ignore it fall back to the system face). No third-party font service, script or tracking pixel; a client that blocks images still reads every fact.
