# RFC-72 — Workspace dashboard

| Field | Value |
|---|---|
| Status | accepted |
| Category | workspace |
| Supersedes | — |

## Context

The workspace landing page still says the research data arrives in a later release. A contributor arriving from an invitation needs, in one screen, what the project is, what their scope is, where data is missing in it, what awaits their validation, and what they have already done; managers and admins need the same screen to say how far the dataset is and what sits in the queues. Every number here comes from a stored counter or a small table (RFC-69), never from a scan of the whole dataset per page load.

## Rules

- **R1** `GET /api/me/dashboard` (`dataset.read`) answers `{ dataset, scope, contributor, curation }`:
  - `dataset: { speciesCount, referenceCount, primaryReferenceCount, secondaryReferenceCount, recordCount, computedAt }` — global counts (active species only for `speciesCount`; `primaryReferenceCount` and `secondaryReferenceCount` count the references whose `primary_count`, and whose `secondary_count`, is above 0, RFC-61 R4), cached one hour in Redis under `stats:dataset` (RFC-69 numbers).
  - `scope: { plots: [{ id, code, name, speciesCount }], speciesCount, restricted } | null` — null when the viewer has no plots.
  - `contributor: { missingCells, awaitingValidation: { count, records: [<record item>…] (≤ 20, newest first) }, topTraitsWithData: [{ trait: { id, key, valueType, unit }, category: { key, label }, speciesCount }] (the ten visible active traits with the most visible species with data — RFC-62 R5's `speciesCount`, from `speciesCountsByTrait` — descending, then by trait key; a trait with no species is left out), summary: <RFC-71 R4> }` — the scope-dependent numbers are computed over the viewer's plot species; for a viewer without plots, `missingCells` and `awaitingValidation` are `null`; `topTraitsWithData` is the same list for every viewer of a visibility class, plots or not. The `contributor` section is cached five minutes per viewer under `dashboard:<viewer id>`, bar the `awaitingValidation` record items: the entry holds their ids and the items are re-hydrated from Postgres on each request, because a record item carries `createdBy.name` and RFC-40 R1 forbids persisting PII in the clear in Redis as much as in Postgres. Creating a record (`POST /api/records`), mapping a pending group (`POST /api/records/pending/map`, which creates records of its own), annotating a record (`POST /api/records/:id/annotations`), validating or withdrawing a level (RFC-65 R13, R14), or changing the viewer's own plots (`PUT /api/admin/users/:id/plots`) drops the entry, so each shows up on that viewer's own next load rather than waiting out the cache. Two other writes leave it stale for the rest of its five minutes and are accepted as doing so: changing which species a plot holds (`POST /api/plots/:id/species`, `DELETE /api/plots/:id/species/:speciesId`) and revoking `dataset.read_inactive`. Both are infrequent administrative actions and both would otherwise have to bust the key of every viewer bound to the plot or holding the role, which is disproportionate to what they change; for at most five minutes, therefore, a restricted viewer's `contributor` section may count — and, in the first case, list — a record on a species that has just left their plots. The window is bounded by the ttl and closes by itself; R2 binds every list the answer computes, and this named five-minute staleness is its one exception.
  - `curation: { coverage: { cells, withData, validated, percentWithData, percentValidated }, queues: { pendingGroups, contested, proposals } } | null` — present for viewers with `records.review`; `coverage` is RFC-69 R5 with no filter (cached); `pendingGroups` counts RFC-65 R8 groups, `contested` the standing contests of RFC-65 R10, `proposals` open proposals (RFC-75), which is `0` for a viewer who does not also hold `taxa.manage` — the proposals queue is that permission's work (RFC-75 R3, R7), and a count for a queue the API would refuse the viewer is worse than no count; the rest of the section stays gated on `records.review` alone.
- **R2** Every list in the answer applies RFC-33 and RFC-67 (plot-bound viewers never receive species outside their plots).
- **R3** The web app greets the viewer by first name ("Welcome back, {first name}") and heads the intro card with "Help complete what we know about how trees reproduce."; under them it renders, across the full width of the card, the project description with the `dataset` counts substituted: "TreeRepro is a collective data assembly of reproductive trait data for trees, covering traits across all reproductive stages — flower, fruits, and seeds. Its core data comes from open-source papers and data repositories spanning {primary} primary references, {secondary} secondary references and {records} records over {species} species. It is shared here with a community of specialists to fill gaps and validate existing records. For questions, contact elisabpereira@gmail.com." Here `{primary}` is `primaryReferenceCount`, `{secondary}` is `secondaryReferenceCount`, `{records}` is `recordCount` and `{species}` is `speciesCount`. Below the text, inside the intro card, are the buttons **Browse species**, **Browse traits** and **Browse references**. The **Top traits with data** card lists `topTraitsWithData`, each trait linking to `/app/traits/$id`. The copy lives in `apps/web/src/content/project.ts` so the owner can edit it in one place.
