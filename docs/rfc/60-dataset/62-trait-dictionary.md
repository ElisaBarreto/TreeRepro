# RFC-62 — Trait dictionary

| Field | Value |
|---|---|
| Status | accepted |
| Category | dataset |
| Supersedes | — |

## Context

Traits are a controlled vocabulary: about one hundred standard traits in thirteen categories, each categorical (a closed list of levels) or quantitative (a number in a fixed unit). The vocabulary is what makes filtering and comparison possible; a value outside it is pending harmonisation (RFC-63 R5), never free text.

## Rules

- **R1** Tables:
  - `trait_categories(key text primary key, label text, sort_order integer)`
  - `traits(id uuid default uuidv7(), key text unique, category_key text references trait_categories restrict, value_type text in ('categorical', 'quantitative'), unit text null, description text default '', active boolean default true, created_at timestamptz, created_by uuid null references users)`
  - `trait_levels(id uuid default uuidv7(), trait_id uuid references traits restrict, key text, sort_order integer default 0, active boolean default true, created_at timestamptz, created_by uuid null references users; unique (trait_id, lower(key)))`
- **R2** The vocabulary is versioned in the repository as `apps/api/seed/trait-dictionary.csv` with the columns `final_standard_trait, broad_category, trait_value_type, standard_unit, description, harmonised_levels` (levels separated by `;`). The command `seed:traits` loads it: it inserts the categories that are missing (label = key with underscores replaced by spaces and initial capitals; `sort_order` = position of first appearance), the traits that are missing (key, category, value type, unit or null, description) and the levels that are missing (`sort_order` = position in the list). It never updates, deactivates or deletes a row and may run any number of times. The keys are stored exactly as the file spells them. The file may carry an optional seventh column `active` (`true` / `false`, case-insensitive; default `true`): `seed:traits` stores it when it inserts the trait and, as before, never updates an existing one. A row whose trimmed `broad_category` is `taxonomy`, `reference` or `record` is skipped: these describe columns of the compiled-dataset file (RFC-64 R2), not traits.
- **R3** A trait or a level is never deleted. Retiring one sets `active = false`: it disappears from the choices offered for new records; records already pointing at it are unaffected. Plan 07 defines the routes that create, rename and retire traits and levels.
- **R4** A value matches a level when `lower(trim(value)) = lower(key)` for a level of that trait.
- **R5** `GET /api/traits?categoryKey=&valueType=&q=` (`dataset.read`) returns the whole dictionary: categories by `sort_order`, each with its traits by `key`, each with its levels by `sort_order` then `key`; the query parameters filter the dictionary server-side (the page still loads it whole for its selects — filtering answers deep links). `q` serves API consumers and deep links: it matches `key` or `description` case-insensitively on the stored key, while the Traits page's own text box filters the dictionary it has already loaded, client-side and on the humanised key, and does not send `q`. For a restricted viewer (RFC-33 R1) inactive traits and inactive levels are omitted; for an unrestricted viewer they are included with `active: false`. Shape: `[{ key, label, traits: [{ id, key, valueType, unit, description, active, speciesCount, levels: [{ id, key, sortOrder, active }] }] }]` — `speciesCount` is the count of visible species with a `species_trait_coverage` row for the trait (`select trait_id, count(*) from species_trait_coverage c join species s … group by 1` is a scan of the coverage table, millions of rows), so it is cached 10 minutes per viewer class (`dictionary:species-counts:<u|r>`, `cachedJson`) rather than computed per request; a fresh number is not worth a scan per form select. Like R7's distribution cache, `speciesCount` is a global summary, never scoped to a plot-bound viewer's plots: such a viewer gets the restricted class (`r`) exactly like any other restricted viewer, and the count still includes species outside their plots — RFC-60 R6 makes the same choice for `traitCount`. The response itself is not cacheable beyond the request (the dictionary is editable, R6).
- **R6** Writes require `traits.manage`, answer the trait entry of R5 (201 on create, 200 on update) and record `traits.created` or `traits.updated` in their transaction (RFC-41 R5) with `target_type = 'traits'`, `target_id` the trait id, `metadata.fields` on update and `metadata.levelId` when a level is concerned. `POST /api/traits` `{ key, categoryKey, valueType, unit?, description? }` (`key` 1–200 characters trimmed, `unit` 1–32, `description` up to 2,000; 409 `TRAIT_KEY_TAKEN`; an unknown category answers 400 `VALIDATION_FAILED` with path `categoryKey`). `PATCH /api/traits/:id` `{ categoryKey?, description?, active? }` (404 `TRAIT_NOT_FOUND`) — `key`, `valueType` and `unit` are immutable after creation: the import matches by key and a unit change would silently change the meaning of stored numbers. `POST /api/traits/:id/levels` `{ key, sortOrder? }` adds a level (default `sortOrder` = the trait's highest + 1; 409 `LEVEL_KEY_TAKEN` on `lower(key)` within the trait) and records `traits.updated` with `fields: ['levels']`. `PATCH /api/traits/:id/levels/:levelId` `{ key?, sortOrder?, active? }` (404 `LEVEL_NOT_FOUND`, also when the level belongs to another trait; 409 `LEVEL_KEY_TAKEN`). Renaming a level keeps every record's `level_id` and `value_text`. A `PATCH` with no field answers 400 `VALIDATION_FAILED`; one that changes nothing records nothing. `seed:traits` (R2) re-inserts a level whose key was renamed unless the repository CSV is changed too: a rename made in the UI is also made in `apps/api/seed/trait-dictionary.csv`.
- **R7** `GET /api/traits/:id` (`dataset.read`, visibility): the trait entry plus `category: { key, label }`, `speciesWithData`, `speciesMissing` (visible species without a coverage row), `validatedCount` (species with a validated species × trait on this trait, RFC-63 R11), and `distribution`: for a categorical trait `levels: [{ level: { id, key }, speciesCount, recordCount }]` (harmonised records grouped by level, species counted distinct); for a quantitative trait `numeric: [{ unit, means: { single, mean, median, min, max }, speciesCount }] | null` over the harmonised records whose `unit_status` is not `needs_unit_check` (RFC-63 R10; a record with `unit_missing` still counts, since the standard unit is assumed) and that carry at least one of single, mean, median, min and max value. These records are grouped by effective unit — the record's `unit` or, when it has none, the trait's standard unit (RFC-63 R1) — and `numeric` holds one entry per unit, `speciesCount` descending then `unit` ascending (a null unit last): numbers in different units are never averaged together. Within one unit, each entry of `means` is the mean of that one field taken per species first: the mean of the field over each species' records — for `mean`, `median`, `min` and `max`, over the species' distinct (`primary_reference_id`, `secondary_reference_id`, value) of that field, so a study's summary repeated on several records counts once (RFC-63 R10) — then the mean of those species means, so every species weighs the same whatever its number of records; a species without the field does not enter that entry, and an entry no species has is `null`. The fields are never pooled — a bound is never averaged with a central value — and `sd_value`, `se_value` and `n` never enter (RFC-63 R15). `speciesCount` counts the species with at least one of the five fields in that unit, whichever it is, so a species with records in two units counts in both; `numeric` is `null` when there is none; and `computedAt`, the moment that distribution was computed. Unknown or invisible → 404 `TRAIT_NOT_FOUND`. Like R5's `speciesCount`, `speciesWithData`, `speciesMissing` and `validatedCount` are global summaries, never scoped to a plot-bound viewer's plots: all three vary only with the viewer's active/inactive class, so such a viewer reads a header that counts the whole dataset while R8's species lists below it stay inside their plots — a plot-bound viewer may see how much the dataset knows, and browse only their own species. The distribution query runs over `trait_records` for one trait through `trait_records_trait_idx`; it is bounded by the largest trait (~1–2% of the records) and cached in Redis for 10 minutes per viewer class (`trait:<id>:distribution:v4:<u|r>`, the version keeping an entry of an earlier shape or rule from being read — plot-bound viewers get the restricted class: the summary is global, not per plot), invalidated by nothing — a ten-minute lag on a summary is acceptable. `speciesWithData` is R5's `speciesCount` for this trait under the header's own name — the same count of visible species with a coverage row, over the same population as `speciesMissing`, so the two add up and the page cannot report one figure in the list and another in the header. `computedAt` is that cache entry's own timestamp rather than the moment of the request, so the lag this rule accepts is legible to whoever reads the page instead of a ten-minute-old summary being shown as current; the counts beside it are read fresh on every request and are not what it dates.
- **R8** `GET /api/traits/:id/species?mode=with|missing&q=&familyId=&genusId=&scope=&plotId=&cursor=&limit=` (`dataset.read`, visibility and plot scope as RFC-33 R6): species list items (RFC-60 R6) plus, in `with` mode, `recordCount`, `validated: boolean` (RFC-63 R11) and `summary: { levels: [{ key, count }] } | { numeric: [{ unit, means: { single, mean, median, min, max } }] } | null` (from the species × trait records, the numeric summary excluding records whose `unit_status` is `needs_unit_check`, grouped by effective unit as R7 — one entry per unit, most records first then `unit` ascending (a null unit last), a unit none of whose records holds a field left out — and giving, per unit and for each of the five fields, its mean over the species' records — for `mean`, `median`, `min` and `max`, over their distinct (`primary_reference_id`, `secondary_reference_id`, value), so a repeated study summary counts once — or `null` when none has it, as RFC-63 R10; computed per page of at most 200 species with one grouped query). `missing` mode is the anti-join on the coverage table. Order and cursor as the species list.
