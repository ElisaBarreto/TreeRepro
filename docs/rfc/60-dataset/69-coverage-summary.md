# RFC-69 — Coverage summary

| Field | Value |
|---|---|
| Status | accepted |
| Category | dataset |
| Supersedes | — |

## Context

Lists that filter or sort by "has data for this trait" cannot aggregate eight million records per request; this table is the maintained answer.

## Rules

- **R1** Table `species_trait_coverage(species_id uuid references species restrict, trait_id uuid references traits restrict, record_count integer not null, harmonised_count integer not null, first_record_at timestamptz not null, last_record_at timestamptz not null; primary key (species_id, trait_id); index (trait_id, species_id))`. One row per species × trait with at least one record. `species.trait_count integer not null default 0` is the number of such rows for the species (RFC-60 R1 amended). The column is visibility-blind by design: being denormalised it cannot be per-viewer, so it counts every coverage row, including rows on traits a curator has deactivated (RFC-33 R2). The filters and the completeness order of RFC-60 R6 do apply species and trait visibility (R4), so the two can disagree for a viewer who cannot see every trait — a species whose only record in a category is on an inactive trait is listed by `categoryKey=…&traitData=missing` while the trait count shown beside it still includes that trait, and the completeness order ranks it accordingly. This is intended: the count is a coarse guide, not a metric shown to contributors (`docs/specs/2026-09-17-browsing-design.md` §2).
- **R2** Maintenance: the statement trigger on `trait_records` insert (the one that maintains RFC-61 R4's counters) also upserts `species_trait_coverage` from the inserted rows (`on conflict (species_id, trait_id) do update set record_count = record_count + excluded.record_count, harmonised_count = …, last_record_at = greatest(…)`) and increments `species.trait_count` by the number of pairs newly inserted. Records are append-only (RFC-63 R4), so nothing ever decrements. Withdrawn records still count: coverage answers "is there a record", not "is there a good record".
- **R3** The migration backfills both in one statement each, the table from `trait_records` and the column from the table. The table first: `insert into species_trait_coverage … select species_id, trait_id, count(*), count(*) filter (where harmonisation = 'harmonised'), min(created_at), max(created_at) from trait_records group by 1, 2 on conflict do nothing`. Then the column, from the table that statement has just filled: `update species s set trait_count = c.n from (select species_id, count(*) as n from species_trait_coverage group by 1) c where s.id = c.species_id` — one grouped pass joined to `species`, not a correlated `count(*)` per species row; a species with no coverage row matches no group and keeps the column's default of `0`. The `treerepro_app` role gets `SELECT` only on the table. The trigger function (`trait_records_reference_usage()`, migration 0015, plain `plpgsql` today) becomes `SECURITY DEFINER` with `SET search_path = public, pg_temp` (the `audit_log_purge` pattern of migration 0007, with `pg_temp` named explicitly and **last**: unless the temporary schema is listed, PostgreSQL searches it *before* every listed schema for relation names, so a caller holding `TEMPORARY` — which `treerepro_app` does, through the default `PUBLIC` grant — could create a temporary table shadowing one this body reads and have a rule or trigger on it execute as the migrator; naming `pg_temp` after `public` leaves it nothing to shadow): it is owned by the migrator role that owns the tables, so the app role's inserts into `trait_records` can maintain a table the app role only reads. The function keeps its name (renaming would need `DROP TRIGGER` / `CREATE TRIGGER`).
- **R4** The table is read by: species filters and order (RFC-60 R6 amended), the missing-traits mode of the trait page (RFC-62 R8), the dashboard (RFC-72) and the coverage metrics (R5–R7, plan 11c). Visibility (RFC-33) is applied by joining `species` and `traits` and filtering on their `active` flags; the table itself has no flags.
- **R5** `coverageTotals(ctx, visibility)` answers `{ cells, withData, accepted, percentWithData, percentAccepted }` over every visible active species × visible active trait; cached 10 minutes under `coverage:totals:<u|r>`. It keeps this signature and stays the dashboard's unfiltered form (RFC-72 R1's `curation.coverage`, no filters). `coverageMetrics(ctx, visibility, filters)` is the filtered form added beside it (plan 11c), where `filters` is `{ familyId?, categoryKey?, plotId? }`; it backs `GET /api/coverage?familyId=&categoryKey=&plotId=` (`coverage.read`, visibility RFC-33): over the visible active species (restricted by `familyId` or `plotId` when given) and the visible active traits (restricted by `categoryKey` when given), it answers `{ species, traits, cells, withData, accepted, percentWithData, percentAccepted, byCategory: [{ category: { key, label }, traits, cells, withData, accepted, percentWithData, percentAccepted }], byTrait: [{ trait: { id, key, valueType, unit }, category: { key, label }, species, cells, withData, accepted, percentWithData, percentAccepted }], computedAt }`. `withData` counts coverage rows in the selection; `accepted` counts species × trait pairs whose current decision is `accepted` (from `accepted_values`, newest row per pair). Each filter is refused the way the rest of the dataset refuses it: an unknown `familyId` → 404 `FAMILY_NOT_FOUND`, an unknown `plotId` → 404 `PLOT_NOT_FOUND`, an unknown `categoryKey` → 400 `VALIDATION_FAILED` with detail path `categoryKey` and message `Unknown trait category`, exactly as the species list answers it (RFC-60 R6); existence is checked before authorisation, so a plot-bound viewer naming a plot that does not exist reads 404 and one naming a plot that is not theirs reads 403.

  Percentages have one definition everywhere this RFC reports them — the totals, each `byCategory` entry, each `byTrait` entry: `percentWithData = withData / cells`, `percentAccepted = accepted / cells`, both integers 0–100 rounded half up (`percentHalfUp`, R5's own helper), `0` for an empty grid. A `byTrait` row is one trait, not a species × trait grid, so its `cells` is the selected species count (not multiplied by a trait count); its `species` field is the number of selected species that have data for that trait, which is the same count as that row's `withData` — not a separate tally.

- **R6** `coverageMetrics`'s answer is cached in Redis for 600 seconds (10 minutes) under `coverage:<u|r>:<familyId ?? '-'>:<categoryKey ?? '-'>:<plotId ?? '-'>` — the viewer class plus the explicit filters, and nothing else. The base species selection is `globalSpeciesVisible`, the same active-only dimension `computeCoverageTotals` already uses and documents (R5); the plot dimension enters the grid only through an explicit `plotId` filter, which is part of the key. This is deliberate: a key holding only the viewer class must never carry a plot-scoped number, because it would be read back by a different viewer — one bound to a different plot, or to none — for whom that number is wrong; keeping the plot dimension out of the base selection and admitting it only as a keyed filter is what keeps the cache honest per viewer. Each segment after the viewer class is written percent-encoded, and the sentinel of an absent filter (`-`) is written `%2D` when it is a filter *value*: `categoryKey` is free text and a category may be created with any key, so a value must be unable to forge another filter set's key — unescaped, `x:<plot uuid>` as a category is byte-for-byte the key of category `x` scoped to that plot, and `-` as a category is the unfiltered key every viewer of the class reads. Two filter sets sharing one entry would be both a wrong answer and a way to write into an answer nobody asked for, which is the same leak this key exists to prevent. `computedAt` says when the entry was computed; the coverage table only grows (R2), so a stale answer only under-reports.

- **R7** `GET /api/coverage/top?mode=missing|least_accepted&limit=` (`coverage.read`) answers the traits with the most visible species lacking data (`mode=missing`, the default) or the lowest accepted share (`mode=least_accepted`), as `byTrait` items of R5's shape, at most `limit` (bounded to 1–50 by `coverageTopQuerySchema`; 10 when the query names none, the ten of RFC-72 R1's own top list) — the manager's version of the contributor's "top missing traits" (RFC-72 R1's `topMissingTraits`). It is the full unfiltered visible grid (the same base selection as `coverageTotals`, not `coverageMetrics`'s filters) — every visible active species and visible active trait — ranked and cut. That grid is `coverageMetrics(ctx, visibility, {})`, so R7 ranks the `byTrait` rows of R6's no-filter entry (`coverage:<u|r>:-:-:-`) instead of computing a grid of its own: the scope of this answer *is* the no-filter scope R6 already keys, and the coverage page asks for both within one load. Computing it separately would run a `distinct on` over `accepted_values` and a group-by over `species_trait_coverage` on every page load and every mode toggle, beside a sibling request that is a cache hit — the scan per page load this RFC exists to remove. It follows that a `/top` answer carries R6's staleness and no other: it is the same entry, so the two numbers a page shows can never disagree. Each item's `species` and `cells` follow R5's `byTrait` definition exactly (`species` equals that item's `withData`; `cells` is the visible species count); "most lacking data" ranks by ascending `withData` (equivalently, descending species missing = `cells - withData`), "lowest accepted share" ranks by ascending `percentAccepted`.
