# RFC-65 — Curation

| Field | Value |
|---|---|
| Status | draft |
| Category | dataset |
| Supersedes | — |

## Context

Specialist scientists add trait values with their bibliographic references, validate and contest existing claims, and harmonise the rows the import could not. The platform never picks a value among the claims (RFC-63 R11). Records stay immutable (RFC-63 R4): every step here is an insert into `trait_records`, `record_annotations` or `record_references`, and each row carries its actor and time. No free text enters a value: a manual value is an active level of the trait or numbers in the trait's unit, and the source's wording is kept apart as `raw_value`.

## Rules

- **R1** `POST /api/records` takes the body and source resolution of RFC-70 R1–R3; the value checks below still apply. `value` is `{ levelIds }` (1–20 distinct level ids) for a categorical trait, or `{ quantitative: { single?, min?, max?, mean?, sd?, n? } }` for a quantitative one: at least one of single, min, max and mean; `min ≤ max`; `sd ≥ 0`; `n` an integer ≥ 1 (RFC-63 R15). `rawValue` and `note` are 1–2,000 characters, trimmed. Checks, in order: species (404 `SPECIES_NOT_FOUND`); trait (404 `TRAIT_NOT_FOUND`; inactive → 400 `VALIDATION_FAILED`, path `traitId`); the shape of `value` against `value_type` (400, path `value`); each level belonging to the trait and active (400, path `value.levelIds.<i>`); each number per RFC-64 R6 and the comparisons of RFC-63 R15 (400, path `value.quantitative.<field>`); then the sources per RFC-70 R2 (404 `REFERENCE_NOT_FOUND` or 409 `REFERENCE_IS_PERSONAL`, the detail path naming `sources.references.<i>`, RFC-61 R7). Each record is stored with `origin = 'manual'`, `harmonisation = 'harmonised'`, `created_by` = the actor, `level_id` or the quantitative columns, `record_code` per RFC-63 R12 — one `nextval('record_code_tr_seq')` per form, taken for the records actually created and suffixed when there are several (`nextRecordCodes(tx, count)`), and `value_text` = the level key or the text of RFC-63 R15, a number printed as PostgreSQL prints `numeric` (`1e3` is stored as `1000`). Answers 201 with `{ created, validated, duplicates }` per RFC-70 R3.
- **R2** (retired) An entry that matches an existing record is no longer an error: it becomes a validation or a reported duplicate (RFC-70 R3), and `RECORD_DUPLICATE` is no longer answered. Plan 13g retags or removes the code tagged with this rule.
- **R3** `POST /api/records/:id/annotations` appends one of `{ kind: 'confirm', referenceSource? }` or `{ kind: 'withdraw' }`. There is no `note`. `neutral`, `dispute` and `resolve` answer 400 `VALIDATION_FAILED` with path `kind` (Keep both acts on a contest, R16). `confirm` is a validation. `referenceSource` is an optional supporting reference — one source entry of RFC-70 R1 (`{ id }`, `{ doi }` or `{ isbn, citation }`) — resolved per RFC-80 R5 or RFC-61 R10 and stored in `reference_id`. The record's author cannot validate it (403 `PERMISSION_DENIED`). A `confirm` the actor has already given on the record, with the same reference or with none, inserts nothing and gets the same answer as the first. An actor counts once per record however many references they give (RFC-63 R8). A validation is never undone. `withdraw` is R4. The permission split is RFC-70 R4. An unknown or invisible record answers 404 `RECORD_NOT_FOUND`. A withdrawn record is invisible (RFC-63 R13), so it answers 404 too. `confirm` answers 201 with the record detail; `withdraw` answers 200 `{ data: null }`.
- **R4** Withdrawal carries no note: the web app asks only for a confirmation (RFC-70 R9). A record's `created_by` may withdraw their own records. A holder of `records.withdraw` may withdraw any record with `origin = 'manual'`, and a holder of `records.withdraw_imported` any record with `origin = 'import'`. Anyone else answers 403 `PERMISSION_DENIED`. The withdrawn record leaves the dataset (RFC-63 R13). Withdrawing every record a contest created ends the contest, and R16 withdraws a contest as a whole (RFC-63 R14).
- **R5** (retired) Disputes are removed (RFC-63 R7). A record's standing is its contested flag (RFC-63 R14), which no actor sets by hand. Plan 13g removes the code tagged with this rule.
- **R6** (retired) There is no accepted value (RFC-63 R11). `GET` and `PUT /api/species/:id/traits/:traitId/accepted` go away with `accepted_values` and `accepted.manage`. Plan 13e removes the code tagged with this rule.
- **R7** A record is *pending* when its `harmonisation` is `unknown_level`, `multi_value` or `not_numeric` and no record names it in `supersedes_record_id` (RFC-63 R1). `empty` records are never pending: there is nothing to map. A record that supersedes another is its harmonised reading: same species, same primary and secondary references, `raw_value` = the superseded record's `raw_value` or, when that is null, its `value_text`. The superseded record keeps its own review state (RFC-63 R6) untouched.
- **R8** `GET /api/records/pending/traits` (`records.review`) answers `[{ trait: { id, key, valueType, unit }, count }]` for every trait with at least one pending record, `count` descending then key ascending, unpaginated. `GET /api/records/pending?traitId=&cursor=&limit=` (`records.review`; `traitId` required, unknown → 404 `TRAIT_NOT_FOUND`) answers that trait's pending groups `{ valueText, harmonisation, count, sampleRecordId }` — one per distinct `value_text`, `count` descending then `valueText` ascending, composite cursor `[count, sampleRecordId]` (the sample record's `value_text` is the group's secondary sort key, so the keyset predicate re-derives it from the id and stays consistent with the order) (RFC-11 R6); `sampleRecordId` is the newest pending record of the group.
- **R9** `POST /api/records/pending/map` (`records.review`) takes `{ traitId, valueText, value, note? }` where `value` is `{ levelIds }` (1–20 distinct ids) for a categorical trait or `{ numeric }` for a quantitative one, validated as in R1 (inactive trait, foreign or inactive level, number rule). In one statement it inserts, for every pending record of the group (same `trait_id`, same `value_text`) and every chosen level (or the one number), a manual record per R7 with `supersedes_record_id` set and `note` copied, `ON CONFLICT ON CONSTRAINT trait_records_claim_key DO NOTHING`. Answers 200 `{ created, skipped }`: `created` the rows inserted, `skipped` = pending × chosen − created (claims that already existed; their pending originals stay in the queue for a manual decision). An empty group answers `{ created: 0, skipped: 0 }`. Each record it creates takes its own code from the column default (RFC-63 R12, no suffix), and its `{ numeric }` fills only the single value (RFC-63 R15).
- **R10** `GET /api/records/disputed?cursor=&limit=` (`records.review`) lists the standing contests (RFC-63 R14) on species and traits visible to the viewer, newest first, with a keyset cursor on the contest's `id`. A contest is listed only when its species, its trait and every level it names are visible to the viewer (RFC-33 R2). Item: `{ id, species: { id, canonicalName }, trait: { id, key }, createdBy: { id, name }, createdAt, levels: [{ levelId, key, contested }] | null, target: <record item> | null, records: [<record item>…] }`. `id` names the contest in R16. For a categorical contest, `levels` lists every level it contests, by key, each with `contested` telling whether that level still is (RFC-63 R14), and `target` is null. For a quantitative contest, `levels` is null and `target` is the record it responds to. `records` lists the visible records the contest created, by `record_code`: empty for a contest that created none, the one contest record for a quantitative trait. From an item a reviewer resolves the contest per R15: Keep both or Withdraw contest (R16), or Withdraw level (R14) on a level it contests.
- **R11** Representations. The record detail (RFC-63 R8) adds `supersedes: { id } | null` and `supersededBy: [{ id }]`. Map result: `{ created, skipped }`. Pending trait and pending group: as in R8. Nullable fields are `null`, never omitted. The record items answered to a creator (R1, RFC-70 R3) and the detail answered to an annotator (R3) carry user names (RFC-63 R8); `records.create` and `records.annotate` are expected to be granted together with `dataset.read`.
- **R12** Record and annotation writes emit no audit-log entry (RFC-41): the append-only rows carry actor and time and are the provenance.
- **R13** Validate a level. `POST /api/species/:id/traits/:traitId/levels/:levelId/validate` (`records.annotate`) takes `{ referenceSource? }` as in R3. In one transaction it writes a `confirm` on every visible record of that species, trait and level that the actor did not create and has not yet validated. An unknown or invisible species or trait answers 404 `SPECIES_NOT_FOUND` or `TRAIT_NOT_FOUND`. A level that is not the trait's answers 400 `VALIDATION_FAILED` with path `levelId`. A level with no visible record for the species answers 404 `RECORD_NOT_FOUND`. A level whose visible records are all the actor's own answers 403 `PERMISSION_DENIED`. Answers 201 `{ validated: [{ recordId, recordCode }] }`, which is empty when the actor had already validated every record.
- **R14** Withdraw a level. `POST /api/species/:id/traits/:traitId/levels/:levelId/withdraw` (`records.review`) writes, in one transaction, a `withdraw` annotation on every visible record of that species, trait and level that the actor may withdraw (R4), and on no other record. The errors are those of R13, without the 403. Answers 201 `{ withdrawn: [{ recordId, recordCode }], remaining: [{ recordId, recordCode }] }`, where `remaining` lists the visible records of the level the actor may not withdraw (records the actor may not withdraw under R4, such as imported records for a manager); they stay in the dataset, and the level stays contested while any remains (RFC-63 R14). When `remaining` is not empty the web app says "<n> records remain that you cannot withdraw — an admin can withdraw them, or use Keep both".
- **R15** Resolve. A holder of `records.review` resolves a standing contest (RFC-63 R14) in one of two ways: by withdrawing one side — the contest (R16) or a level it contests (R14) — or by **Keep both** (R16), which resolves the whole contest and clears every level it names. A level's contested flag clears once no standing contest names it: each contest naming it is withdrawn or resolved, or the level is left with no visible record (RFC-63 R14). A resolution is never undone.
- **R16** Contest actions. `POST /api/contests/:id/resolve` (`records.review`) is **Keep both**: it marks the contest resolved (RFC-63 R14); on a contest already resolved it changes nothing and gives the same answer. `POST /api/contests/:id/withdraw` (`records.annotate`) is **Withdraw contest**: in one transaction it writes a `withdraw` annotation (R4) on every visible record the contest created or, for a contest that created none, withdraws the contest itself. The contest's author or a holder of `records.withdraw` may withdraw it (a contest is manual, R4); anyone else answers 403 `PERMISSION_DENIED`. `:id` is the contest's `id` of R10. An unknown or withdrawn contest, or one whose species, trait or any named level the actor cannot see (RFC-33 R2), answers 404 `RECORD_NOT_FOUND`. Both answer 200 `{ data: null }` and write no audit entry (R12). How a resolution and a contest that created no record are stored is plan 13g's choice. For a quantitative contest, `id` is its contest's own `id` in the same storage as a categorical one. A resolved contest may still be withdrawn.
