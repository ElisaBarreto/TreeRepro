# RFC-64 — Bulk import

| Field | Value |
|---|---|
| Status | draft |
| Category | dataset |
| Supersedes | — |

## Context

The compiled dataset is one CSV of about eight million denormalized rows. It is loaded once by an administrator, occasionally again when a new compilation arrives. Every row must end up in the database: conforming rows as harmonised records, non-conforming ones as records pending harmonisation, and only rows that cannot be attached to a species, a trait or a reference as rejections that keep the raw row.

## Rules

- **R1** Command `pnpm --filter @treerepro/api import:records --file <path> [--run-by <email>] [--force] [--replace | --replace-imported]`, run inside the API container with the `treerepro_app` role, or with the `treerepro_migrator` role when `--replace` (R12) or `--replace-imported` (R15) is passed. Exit codes: 0 completed, 1 refused or failed, 2 usage. `--run-by` names the administrator running it (stored as `run_by`; unknown email → null with a warning).
- **R2** Preconditions, checked before any batch row is created: the dictionary is loaded (`traits` is not empty) and the first line of the file, parsed as a CSV record, equals exactly, in order: `"", primary_reference, secondary_reference, wcvp_species, wcvp_genus, wcvp_family, gbif_species, gbif_usage_key, original_species_name, secondary_source_species_name, original_trait_name, final_standard_trait, broad_category, original_value_clean, trait_value_type, harmonised_value, ID` — the unnamed first column is R's row number, read and ignored (it is never stored in `raw_row`).
- **R3** Table `import_batches(id uuid default uuidv7(), file_name text, file_sha256 text, kind text not null default 'records', run_by uuid null references users, started_at timestamptz default now(), finished_at timestamptz null, status text in ('running', 'completed', 'failed') default 'running', error text null, rows_total bigint default 0, rows_inserted bigint default 0, rows_duplicate bigint default 0, rows_rejected bigint default 0, rows_pending bigint default 0, rows_already_imported bigint default 0, unknown_levels jsonb default '[]')`, `kind` checked against the kinds of RFC-68 R1. One row per run. A `completed` batch with the same SHA-256 of the file refuses a new run (exit 1, the existing batch id printed) unless `--force` or `--replace` (R12, which deletes that batch). `mode` is `append` or `replace`, recording how the run treated earlier imports.
- **R4** Staging: the file is streamed with `COPY … FROM STDIN (FORMAT csv, HEADER true, ENCODING 'UTF8')` into a session temporary table with a serial `row_no`; `row_no` 1 is the first data row. The file is never held in memory.
- **R5** Resolution per row, after trimming and collapsing whitespace (RFC-60 R2): the species name is the first non-empty of `wcvp_species`, `gbif_species`, `original_species_name`, `secondary_source_species_name`, with `name_source` `wcvp`, `gbif`, `original`, `original` respectively; genus and family come from `wcvp_genus` and `wcvp_family`; `gbif_species` different from the species name becomes an alternative name with `gbif_usage_key`; references are matched by trimmed `citation_key` for `primary_reference` and `secondary_reference`; the trait is matched by `final_standard_trait`. Missing families, genera, species, alternative names and references are inserted; existing rows are never changed by an import.
- **R6** Harmonisation per RFC-63 R5, with the level match of RFC-62 R4 and the number rule: the trimmed value has at most 64 characters, matches `^[+-]?([0-9]+\.?[0-9]*|\.[0-9]+)([eE][+-]?[0-9]{1,3})?$` and its magnitude is below `1e308` (so the value casts to `numeric` and fits `double precision`); anything else is `not_numeric` (a decimal comma is not a number). Manual entry (RFC-65 R1) applies the same rule. Every value is trimmed with internal whitespace collapsed to one space before any matching, so `woody   shrub` matches the level `woody shrub` whether or not it arrived inside a `;` list. A categorical value containing `;` is split on `;` before the level match of RFC-62 R4: each part is trimmed, empty parts are dropped, and every remaining part becomes its own record carrying the staged row's `row_no` and `raw_value`, harmonised independently (so one part may be `harmonised` while another is `unknown_level`). A categorical value whose parts are all empty yields one `empty` record. Quantitative values are never split; a `;` in one leaves it `not_numeric`. A quantitative value fills only the single value, `numeric_value` (RFC-63 R15). The records of a split row carry the codes of RFC-63 R12.
- **R7** Rejections, stored in `import_rejects(id uuid default uuidv7(), batch_id uuid references import_batches restrict, row_no bigint, reason text in ('no_species_name', 'unknown_trait', 'no_reference', 'unknown_species', 'unknown_plot', 'unknown_user', 'unknown_reference', 'doi_taken', 'invalid_value', 'invalid_record_id', 'duplicate_record_id'), raw_row jsonb, created_at timestamptz)` with the raw row as a JSON object keyed by column name: no species name in any of the four name columns; `final_standard_trait` not in the dictionary; both reference columns empty; `ID` empty or not matching `^EB_[0-9]+$` (`invalid_record_id`); an `ID` already given by an earlier row of the file (`duplicate_record_id`, RFC-63 R12) — an `ID` already stored is not a reject but R14; the reasons `unknown_species`, `unknown_plot`, `unknown_user`, `unknown_reference`, `doi_taken` and `invalid_value` belong to the supplementary kinds of RFC-68 R4. The first applicable reason in that order is recorded.
- **R8** Insertion: `INSERT … SELECT … ORDER BY row_no ON CONFLICT ON CONSTRAINT trait_records_claim_key DO NOTHING` with `origin = 'import'`, the batch id, `row_no` and `record_code` from the row's `ID` (RFC-63 R12). Counts: `rows_total` = staged rows; `rows_rejected` = rejects; `rows_inserted` = records the insert returned, which may exceed the staged rows because R6 splits a value into several records; `rows_duplicate` = total − rejected − `rows_already_imported` (R14) − the number of distinct staged rows that produced at least one record; `rows_pending` = inserted rows whose `harmonisation <> 'harmonised'`; `unknown_levels` = the 30 most frequent `{ trait, value, count }` among this batch's `unknown_level` records.
- **R9** Staging, resolution, rejection and insertion run in one transaction. Any failure rolls it back, sets the batch to `failed` with the error message, and exits 1; nothing of the batch remains in the data tables. Re-running after a fix is safe (R3, RFC-63 R3).
- **R10** On completion the batch is `completed` with `finished_at` and the counts, and the command prints: file, batch id, elapsed time, the six counts (R8, R14), the count per harmonisation status, the unknown levels by trait, and rejections by reason.
- **R11** `GET /api/imports?kind=&cursor=&limit=` (`imports.read`) lists batches newest first (keyset on `id`), optionally filtered by `kind` (RFC-68 R7): `{ id, fileName, fileSha256, kind, status, runBy: { id, name } | null, startedAt, finishedAt, rowsTotal, rowsInserted, rowsDuplicate, rowsRejected, rowsPending, rowsAlreadyImported, unknownLevels, error }`. `GET /api/imports/:id` returns one; `GET /api/imports/:id/rejects?cursor=&limit=` lists `{ id, rowNo, reason, rawRow }` by `row_no` ascending (keyset on `row_no`, then `id`). Unknown batch answers 404 `IMPORT_NOT_FOUND`.

- **R12** `--replace` empties everything earlier imports loaded before this file is staged, in the same transaction, so a failure anywhere in the run rolls the wipe back and the previous dataset survives; an import can never leave the database empty. Truncated together, as one foreign-key closure: `record_annotations`, `record_references`, `reference_traits`, `species_proposals`, `trait_records`, `species_trait_coverage`, `import_rejects`, `user_plots`, `plot_species`, `plots`, `species_names`, `species`, `genera`, `families`, `bibliographic_references`. `import_batches` is not truncated — the running batch's row predates the transaction so that R9 can still mark it `failed` — and every other batch is deleted instead. Untouched: `users`, `roles`, `permissions`, `traits`, `trait_levels`, `trait_categories`, `audit_log`. The wipe crosses the append-only guarantee of RFC-63 R4, whose triggers fire for the table owner too, so the run disables them inside its transaction and restores them there; that is why a replacing run uses the `treerepro_migrator` role and `treerepro_app` keeps holding no `UPDATE` or `DELETE` on those tables. `--replace` is refused when `NODE_ENV` is `production`. The refusal is enforced inside the import itself, before any batch row is created, so a caller that is not the CLI cannot reach the wipe either; the command repeats the check first so it can exit 1 with a message. A production container also carries no migrator secret, so the flag cannot work there even if both checks were bypassed. The total `--replace` is refused (exit 1, before anything is written) whenever a `trait_records` row with `origin = 'manual'` exists: it serves the test phase only, and later reimports use R15. The owner's one-time reimport of the record model revision (spec 2026-09-25 §5) is the single sanctioned exception to the production refusal: it follows the runbook "Replacing the imported data with the ID-carrying file" in `docs/gotchas/import.md` (backup, a check that no manual record, annotation or `record_references` row exists, and a one-off container with `NODE_ENV=development` and the migrator secret mounted).

- **R13** One import at a time. A run takes the session advisory lock `4664` on a connection reserved for it — so the pool must allow a second connection for the run's own work — before its batch row is created and holds it until the batch is recorded `completed` or `failed`, for every mode alike, `--replace-imported` included. Without it a replacing run's deletion of earlier batches (R12) can remove the row of an import that is still running, whose own status update then matches nothing and whose batch reads as vanished.

- **R14** Incremental import. A row whose `ID` is already stored as a `record_code` — bare (`EB_4`) or as the base of a suffixed code (`EB_4a`, RFC-63 R12) — is skipped: it creates no record and no reject, and is counted in `import_batches.rows_already_imported` (`bigint not null default 0`). The batch report prints that count as `already imported`, so a full file holding old and new rows can be sent again and only the new `EB_n` IDs are added. An `ID` repeated within the file is still rejected (`duplicate_record_id`, R7). The skip is decided once the `ID` passes R7's `invalid_record_id` and `duplicate_record_id` checks, and before every other reason: an `ID` repeated within the file is rejected even when it is already stored.
- **R15** Replace that preserves the platform. `import:records --replace-imported` replaces the imported (`EB_`) records and keeps everything users produced. In one transaction:
  1. write the **annotation sheet** `replace-<batch>-annotations.csv`: every validation, contest, resolve and withdrawal on an `EB_` record, and every quantitative `TR_` contest responding to an `EB_` record (`record_code, kind, user_name, date, reference, contest_record_code`); a categorical contest names levels, not records (RFC-63 R14), so the replace leaves it untouched, and it contests a level again once the new file gives that level a visible record;
  2. delete the `EB_` records and their annotations only (species, genera, families, references, plots, plot species, user plots, synonyms, proposals and every `TR_` record stay; the file adds what is missing);
  3. import the new file;
  4. **re-link by `record_code`**: annotations and quantitative `TR_` contests pointing to an `EB_n` present in the new file are attached to the new record; the ones whose `EB_n` is gone are marked `orphan` in the sheet and dropped, and an orphaned `TR_` contest becomes an independent record (intent and target cleared);
  5. recompute the counters (`species_trait_coverage`, `species.trait_count`, reference usage counts, `reference_traits`).

  Runs as `treerepro_migrator` through the runbook's one-off container, production included, after a `pg_dump`. The total `--replace` (R12) is refused whenever a `TR_` record exists — it is for the test phase only.

## Open questions

Tolerating a decimal comma and mapping known aliases (`bees` → `bee`) at import time are deferred; curators resolve them in plan 07. R15 does not yet say what becomes of a `TR_` complement responding to an `EB_` record or of a `TR_` harmonised reading superseding one (RFC-65 R7, R9); both columns are foreign keys, so step 2 cannot delete such an `EB_` record. Plan 13k settles it with the owner before coding.
